# Intake, implementation, and verified closure

## 1. Resolve identity and permission

Read the invocation contract and `progress.md`. GitHub issues are the sole durable task-progress authority; local files hold recovery/evidence receipts only. Record the current checkout's repository/common directory, remotes, current branch, and clean/dirty state without changing them. Resolve its GitHub identity through `npx -y gh-axi repo view` and read-only `api GET /repos/<owner>/<repo> --full`. With multiple plausible remotes, fork/upstream disagreement, or an explicit repo not matching this checkout, stop and ask which checkout belongs to that repo. Do not clone or switch someone else's checkout implicitly. Record GitHub's `full_name` and `default_branch`; ignore a local branch named main/master or a stale remote HEAD as a default-branch oracle. Read and verify the selected base and landing branch via GitHub, URL-encoding branch names in API paths. Missing or unreadable branches fail closed. Compare the result with the user's request.

Record authorization for implementation, bounded issue progress comments, feature-branch push/PR publication, landing, and completed closure separately. Before implementation, progress-comment authority must cover the selected issues and necessary parent/blocker mappings; otherwise hold after read-only intake. A run request may include these permissions; absent authority for a later action means hand back the packet before that action. Do not change protections, permissions, labels, assignments, milestones, or issue structure to get past a gate.

## 2. Freeze the inventory

Use the installed CLI help, not guessed flags. The compact `issue list` and `pr list` default to 30 and are not proof of complete inventory. For the snapshot prefer read-only, fully paginated API requests (substitute only the verified repo):

```text
npx -y gh-axi api GET /repos/<owner>/<repo>/issues?state=open&per_page=100 --paginate --full
npx -y gh-axi api GET /repos/<owner>/<repo>/pulls?state=all&per_page=100 --paginate --full
```

These are **argv examples, not unquoted shell commands**: pass each entire API path as 1 quoted argument (the `&` must never background the process). REST's issues collection includes PRs; exclude rows carrying `pull_request`. Preserve complete response fields and page boundaries; gh-axi output is not assumed to be raw JSON. Use `api --jq` only with an explicitly checked projection and inspect the response format before normalization. Never feed abbreviated display text directly to the planner. Keep a page ledger (endpoint, page/cursor, response status, count, stable ids, completion), and reconcile deduplicated counts. Follow all pagination links or cursors; absent access is unknown, never an empty list. A failed page invalidates completion.

For every collected issue row (selected or graph context), enumerate children and dependency relationships completely before marking the snapshot complete. For each selected issue, also read the complete body and **every page of comments**, labels, assignees, milestone, and linked parents/children. `issue view <n> --comments --full -R <repo>` and `issue subissue list <n> -R <repo>` help inspect; neither proves graph pagination. Use paginated GET endpoints for `issues/<n>/comments`, `issues/<n>/sub_issues`, and `issues/<n>/dependencies/blocked_by` where available; read installed API help and confirm the GitHub endpoint's actual support/format. Also inspect `blocking` relationships when needed to map downstream work. A 403/404/unsupported dependency endpoint is not “no dependencies”: stop graph completion and ask for an authoritative dependency mapping or access; record its provenance. No speculative POST to discover read schema. Fetch closed and out-of-selection referenced issues separately as context. Deduplicate by canonical repository + issue id/number, not title. Children are structural, dependencies order work, and ambiguous “blocked by” body links need human confirmation, not guessed direction. Cycles in either graph stop planning. A cross-repo edge is retained as `externalPrerequisites` in qualified OWNER/NAME#number form (including external child requirements), with its relationship/provenance in the ledger. It blocks that issue and propagates to its dependents while independent local issues may continue; it is never a same-number substitute.

Reconcile current issue progress from the complete histories and governing parent decisions under `progress.md`. Missing or conflicting progress is unknown; an open flag is not ready. Deferred, blocked, active-owned, review-held, landed-awaiting-validation and completed issues cannot enter implementation batches. Explicit/parent selection does not override them. A generic continue never supersedes a deferral or replenishes exhausted cycles. Synchronize any new user stop immediately: stop affected work first, then publish/read back its progress record with authority; failed synchronization holds further dispatch.

Snapshot selection once. A parent traversal continues until every recursive child's children were enumerated, even when a child is closed. Filters never prune explicit/parent selectors. Default all-open includes parent issues too; their children are prerequisite/context rather than assumed extra authorized targets. Newly opened issues after the snapshot are deferred to a future run; don't keep extending the queue forever.

## 3. Establish PR coverage before coding

Inspect all relevant open, closed-unmerged, and merged PRs, not only PR titles. Read every page of PR files, comments, reviews, review comments, commits, and checks/statuses; use `pr view <n> --full --comments --reviews --checks -R <repo>`, `pr diff <n> --full -R <repo>`, and paginated API detail when wrappers don't prove completeness. Inspect PR 7 if it exists in the selected repo; a confirmed absence is a fact, not a task failure. Permission/network failure is unknown. Never assume it is open, merged, or relevant from its number.

Map issue → PR, state, head SHA, base, changed paths, asserted closing references, reproduced acceptance criteria, tests, and actual target presence. A reference alone is candidate coverage. Check assertions and code. A merged PR on another branch is not coverage on the selected landing branch. A closed unmerged PR is not a fix. An open equivalent PR means coordinate with its owner, avoid duplicate implementation, and wait for review/landing; don't take over or retarget it without permission. A verified already-landed fix can go through landed-result validation and authorized closure without another PR. If verification exposes a partial fix, keep the issue open and add only the missing work in a new bounded PR.

## 4. Plan and delegate

Build the normalized snapshot in `contract.md`, including every row's current GitHub `progress`, and use the pure `scripts/plan.mjs` exports to check it; it performs no GitHub actions. Respect both progress `held` mappings and dependency blockers. Record their concrete reasons and next steps on the corresponding issues, not a local task ledger. All assertions of completeness and `verified` require reconciled observations. An in-repo prerequisite whose fix is verified on the selected target is satisfied regardless of whether the GitHub issue is still open. Out-of-selection unverified prerequisites, unverified closed prerequisites, and qualified external prerequisites block their dependents. Record concrete mappings such as issue 42 → prerequisite 39 → missing permission/test/landing, and continue independent work only if identity/inventory are complete. Empty selection is a no-op, not a prompt to broaden scope.

Before creating a dependent worktree, prove its **actual starting tree contains its prerequisite fixes**; target verification alone is not an implementation baseline. If base equals landing, refresh the selected remote base after prior prerequisite landing, record the new SHA, and verify prerequisite commit/content inclusion in that starting tree. If base differs from landing and lacks those fixes, hold the dependent issue or obtain explicit authorization for a tightly coupled integration strategy (implement prerequisites first on the same scoped branch, or an approved isolated integration branch starting at the selected base and incorporating those fixes). Do not silently cherry-pick, change base, or broaden scope. Validate the dependency behavior in that actual starting tree before assigning dependent work. Within a coupled branch, each dependent worker starts only after the prior worker's prerequisite change is present and checked in its assigned tree.

Before every worker dispatch or dependent worktree creation, reread issue progress, coordinate ownership, publish/read back the bounded active claim and recheck for competing claims or newer stops under `progress.md`. Initial ready-to-active selection, same-owner active continuation/context replacement, same-owner authorized review repair, and different-owner transfer follow its distinct protocols. Continue an already assigned frozen batch only with recoverable authorization and remaining shared per-batch counters; never fabricate a ready snapshot for an active/review issue or replenish counters for a replacement worker. A different owner requires explicit handoff/user transfer and a superseding issue record. No unresolved hold may be bypassed by a local checkpoint, generic continue request or new run id. Comments are not an atomic distributed lock; unresolved competing ownership stops overlap; never steal a claim.

Create tracked, isolated worktrees from that verified selected-base/integration tree with the supported worktree tool after reading its current schema; verify HEAD and branch immediately. If the tool cannot select that base, stop or use an operator-created isolated checkout—never let a default master silently substitute. Do not write implementation in the main/live checkout. One issue or a tightly coupled, reviewable batch per branch. At most 2 implementation workers simultaneously; within each planned batch, dependencies run serially and overlapping ownership never runs concurrently. At most `maxBatches` batches, even if many issues remain. Before dispatching a later batch, require its prerequisite batches' fixes to have passed the reviewed landing/result gates on the selected target, then rebuild prerequisite verification at the current target SHA. A failed/unlanded prerequisite blocks downstream batches. Within a tightly coupled single-PR batch, implement dependencies serially and validate the whole batch together; do not claim its dependents landed before the PR lands. Send workers issue URLs and effective progress comment ids, literal issue acceptance criteria, relevant read spec passages and unknowns, scoped issue numbers/paths, base/landing SHA and names, existing PR coverage, authorization limits, and the testing plan. Workers report evidence to the owning resolver; they do not keep an independent task-status ledger. Workers cannot push, merge, close, restart, deploy, or touch foreign worktrees. Require a checkpoint before 50% context; fresh worker handoff, not indefinite resumption.

Each worker reproduces the issue, reads current assertions/source, makes a feature spec draft before behavior edits, implements the smallest fix, adds regression tests that distinguish the bad behavior, and uses the repository's tools in its own checkout instance. For Sova use `project_verbs test` on that instance; no manual test runner or ad-hoc server. Typecheck/build, relevant unit and changed integration coverage, and applicable extension suites follow guidance. Never run Sova's spec replay while developing; it is a landing gate. Record exact code/base SHA, commands, exit results, and what was not checked. A red/flake in product code is a product behavior fix, not an excuse to weaken assertions. Spec evidence is tied to the eventual implementation commit; no fabricated commit and no “tool check proves correctness.” Only the owning session promotes verified promises under spec rules.

Independently review the issue-to-diff-to-test mapping, leak risks, and spec promises. If a separate reviewer isn't available, report that limitation and wait for the required human review; do not relabel self-review as independent. At most 2 repair cycles per batch, then publish/read back blocked or deferred progress with unresolved findings and remaining/exhausted budget, and stop that branch. Preserve dirty work and earlier failed/review evidence. Reopening requires explicit user authorization naming the affected issue and any new budget, followed by a superseding GitHub record/read-back before dispatch. Review or test results tied to an old head do not count after changes. Workers hand back clean commits only when the run authorized commits; otherwise give the parent the bounded diff and let it commit.

## 5. Publish a reviewable PR or hand off

With publication authority, leak-scan what will be published and push **only the named feature branch** to the verified repo's remote by non-force push. Never push a target branch directly, `--all`, tags, or private run state. If a remote changed/diverged, stop and reconcile with the owner; don't rewrite shared history. Recheck existing PR coverage before creating a PR to avoid a duplicate after a race. Use `pr create` with explicit selected landing as `--base`, exact feature `--head`, and a body file. Include acceptance-criteria and test/spec evidence per issue, limits, residual blockers, `Refs owner/repository#42`, and a closure-candidate matrix. Publish **no triggering `Fixes`/`Closes`/`Resolves` references before landed-result tests pass and closure is authorized**: GitHub's default-branch auto-close could otherwise happen before the gates. Audit existing PR body and commit messages for triggering keywords too; an existing PR that can auto-close must have its owner remove/defer those references with permission, or remain on hold. Do not mutate someone else's PR/commits or accept premature closure as a shortcut. After verified landing and closure authority, update the authorized PR body with fully-qualified `Fixes owner/repository#42` for each wholly fixed issue, preserving prior review evidence. Partial fixes stay `Refs`. A parent gets a closing reference only after its entire tree and its own requirements are satisfied. Require independent review and all repository-required CI at that head; draft or unresolved-review PRs are not landable.

`landingMode: "handoff"` creates a packet, not a local merge: repo, base/landing branches and SHAs, feature head, PR, issue matrix, tests, review/CI status, spec draft ownership, leak-scan result, exact authorization, and unresolved blockers. Give it to the named idle landing owner; otherwise return it to the user. Merge captain is eligible **only for the Sova repo and master with verified origin/master**, not other repos or release/main targets. Its master-specific driver is not called by this resolver. Verify captain identity/ownership through permitted session detail/read and ask only while idle. Its ordinary recipe pushes, cleans up, and restarts; therefore require an explicit acknowledgement agreeing to **only the named reviewed head/PR, selected target, required protected review/CI path, and no cleanup/restart/deploy** before delegation. It must also acknowledge withholding auto-closing references until landed validation and closure authority. If it cannot accept the narrower operation without conflicting with its recipe, do not hand off: return the packet to the user or use the protected PR path. Never assume a generic READY answer accepts these restrictions. Its READY/check/local merge is not remote landing proof; the resolver revalidates the result independently. No permission to restart/deploy/clean up is passed by this packet.

## 6. Verify landing, then close

In PR mode with landing authority, use the repository's normal protected merge/merge-queue path, never admin/bypass flags, and the installed `pr merge --match-head-commit <reviewed SHA>` guard. Choose only an allowed merge method. Re-read base/head, required reviews, mergeability, and all required checks immediately before requesting merge. A queued `--auto` result means waiting. No polling indefinitely: save state and resume later. Target advancement invalidates any merged-result tests; revalidate. Do not treat protection failure as a signal to change settings or perform a direct target push.

After GitHub says merged, read its authoritative merge commit/result and remote selected landing ref. Fetch the named ref read-only into the isolated repository; verify result reachability on that exact remote target. For squash/rebase, do not demand ancestry of the old feature tip: verify the returned landed commit(s) and issue-specific content/tests. If merge metadata or inclusion cannot be established, leave issues open and report unknown landing. For an already-existing fix, identify its actual target commit and follow the same path. Validate tests/reproductions against that landed result, not the pre-merge feature tree; if the target moved, validate current target coverage too. Required target CI is still a gate. A post-merge regression is unresolved even if GitHub automatically closed the issue: report immediately; reopening requires authorization, never hide the failure.

Close only wholly resolved issues after all landing/result gates. After landed validation and closure authority, add the wholly fixed issues' closing references to the authorized PR body. On GitHub's default branch, read whether that produced automatic closure and verify its linked PR/commit; late references may not auto-close. If still open, with closure authority use `issue close <n> --reason completed -R <repo>` and a factual comment naming PR, landed SHA, selected target, and validation. On a **nondefault landing branch**, GitHub may not interpret closing references: explicitly read the current issue state, perform the authorized completed closure only after selected-target verification, then read back state/reason/timeline and the cited fix. Do not say “closed” from a successful request alone. Cross-check an issue closed by someone else against the requirements; don't count it solely because it is closed. Parents close last, and only after every child and their own acceptance criteria is verified, not just after child status flags change.

Do not close duplicates, wontfix, or not-planned as completed. Those decisions and any scope change need explicit user authorization with issue mappings. Leave blockers open and record progress on their issues under the separately confirmed bounded progress-comment authority; without it, hold and ask for synchronization. Progress-comment authority never implies labels, assignments, issue-body edits, closure or scope changes. Keep worktrees/branches for review/resume; cleanup is a separate authorized, non-force action that respects active owners and git refusals.

## 7. Checkpoint and exit

After each phase, user decision or mutation attempt, publish and read back concise progress/evidence summaries on the relevant GitHub issues under progress-comment authority. Save only local recovery mechanics, authorization/budget provenance, mutation intents and exact evidence receipts described in the contract. Do not write another task-status ledger. Chat/Overseer reports are projections of GitHub progress, with pending updates explicitly named. Reads retry twice at most after the initial failure, respecting rate-limit retry-after; authentication/protection/schema failures do not retry blindly. If a write times out, read its result back before retrying: an ambiguous mutation is pending/unknown, never duplicated automatically. Stop at budget or a blocked gate and return deferred/blocked mappings and the resume id. Resume rereads GitHub progress and verifies live repo/default/branch/PR/issue state and authorization, but preserves the original selected set; any changed intent or newly selected issue is a new authorized run. No background loop, timer, wake schedule, or endless “finish everything” fan-out.
