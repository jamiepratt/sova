# §chat/resolve-github-issues — Resolve GitHub issues

Sova's project bundle `.sova/playbooks/resolve-github-issues/` tells an agent to snapshot and resolve all open issues in the current GitHub repository by default, through isolated implementation worktrees, reviewed PRs, and verified landing before closure. It is instructions, not an autonomous executor or a schedule. Its matching project profile keeps workers, shell, and worktrees available, grants only project-scoped session reading and messaging, is One at a time, and allows Overseer starts subject to project-profile approval (§chat.profiles/trust). The profile supplies a first-message bootstrap that discovers the absolute current checkout root from a subfolder too and reads its bundle; the separately marked invocation JSON supplies arguments. Selecting the profile alone does not run the recipe.

The invocation is empty text or a strict JSON object: explicit `repo`, starting `base`, destination `landing`, a single/list `issues` selector or `parent` plus recursive subissues, conjunctive `filters`, `batchSize`, `maxBatches`, `landingMode`, and `resume`. Defaults discover the repository and its default branch from GitHub, with base and landing each independently defaulting to the discovered default branch and PR landing. Missing targets, ambiguous repository identity, unread inventory pages or dependency edges, and cycles fail closed. A parent includes every recursive descendant, including closed children as verification context; filters do not prune that tree. A qualified external prerequisite blocks its issue and dependents rather than silently expanding scope; independent local work can continue. In-repo prerequisite verification is bound to the selected landing branch and its exact observed SHA, regardless of whether the issue is open or closed.

The bounded pure helper `scripts/plan.mjs` validates normalized requests and complete snapshots, deduplicates identical inventory rows, rejects conflicting rows, and produces deterministic dependency-first batches and issue-to-prerequisite blockers. It never fetches, writes state, spawns workers, lands, or closes anything. The recipe requires the agent to page and deduplicate issue, child, dependency, comment, PR, review, and check inventories, inspect existing PR coverage (including PR 7 when present in the selected repository, never assuming its state), and verify claimed coverage against assertions and source.

Each batch has at most 3 issues by default, at most 2 implementation workers at once, and at most 2 batches per invocation. Transient reads retry at most twice after the initial attempt; each fix gets at most 2 repair cycles. State is local under `<state root>/playbooks/resolve-github-issues/<run>/`, excludes secrets and raw untrusted bodies, and records request, snapshot identities, worktrees, tests, PRs, authorizations, blockers, and verified landing/closure evidence. Resume revalidates identities and current heads, never treats an attempted mutation as completed, and does not refresh the default all-open selection silently.

Workers receive literal requirements and relevant spec passages, unknowns, a bounded issue mapping, and the selected base/landing branches. A dependent worker's actual starting tree must contain the prerequisite fixes: refresh the base after landing when it matches the target, otherwise hold or use an explicitly authorized tightly coupled integration strategy. Target verification alone does not establish an implementation baseline. Tests, spec verification, review, CI, permissions, and leak checks are kept. PR bodies use non-closing references during review and merge so automatic closure cannot outrun closure authority or landed-result validation. After those gates, fully-qualified closing references name only wholly fixed issues, leaving partial fixes and unresolved parents open. Closure requires verified implementation, tests at the landed result, and authoritative evidence that the reviewed fix reached the selected remote target; nondefault landing requires an explicit completed closure and read-back, since automatic GitHub closure is not assumed. Duplicates, wontfix, scope changes, force, protection bypass, and destructive cleanup are never implicit authorizations.

Sova's merge-round is master-specific (§chat.merge-round/driver), not a generic alternate-branch landing mechanism. `landingMode: "handoff"` reports an explicit target/head/issue/evidence packet to an idle, verified landing owner; merge-captain is eligible only for this Sova repository targeting master and only after explicitly acknowledging the restricted protected landing operation with no cleanup/restart/deploy or premature automatic closure. Without that acknowledgement, the resolver returns to the user or protected PR path. The resolver never invokes its driver, rewrites it, or treats the handoff as landing. The resolver does not restart or deploy live Sova; hosted workers are server children and must not be killed by a restart. Sandbox or capability denial becomes a mapped blocker, never a request to lower containment.
